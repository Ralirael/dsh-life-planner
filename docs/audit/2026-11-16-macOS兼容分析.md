# macOS 兼容性分析（2026-11-16，对比 0.9.33-macos 适配包）

> 目的：判断 `MacOS/` 里那份"为 macOS 26 单独改过"的 0.9.33 构建，哪些差异能通过**改进写法**
> 合并回单一主线（一个包同时跑 Windows/macOS），哪些属于打包/平台事实、无法靠写法消除。

## 1. 结论

| 类别 | 数量 | 结论 |
|---|---|---|
| 可以用写法兼容（已合并进主线 **0.9.35**） | 7 | 通知、PDF、书架去重、安装门槛、预设缺包、提示词、文案 |
| 打包层差异（与代码兼容无关） | 3 | 依赖随包、符号链接扁平化、`.command` 安装器 |
| 平台事实 / 未解决 | 2 | Windows/Linux 的桌面通知、PDF 在 Linux 仍需 poppler |
| 确认本来就兼容 | 7 | 背景图、模板、快捷键、字体、学习日、打开文件、目录扫描 |

## 2. 已合并进主线的 7 项（改写法即可跨平台）

| # | 项 | macOS 适配包的做法 | 合并后的写法 | 为何不破坏 Windows |
|---|---|---|---|---|
| 1 | 系统通知 | `hostNotify` 失败后走 `osascript` | `hostNotify` → Electron 失败时 `platformNotify()`，只在 `darwin` 且存在 `/usr/bin/osascript` 时执行 | win32 无该分支，行为不变 |
| 2 | PDF 取文 | 新增 PDFKit（JXA + ObjC）引擎 | `readPdfText()`：先 `pdftotext`，失败再 `pdfKitText()`（仅 darwin）；返回 `engine` | Windows 仍走 pdftotext，缺引擎时给同样的可读错误 |
| 3 | pdftotext 搜索 | 补 `/opt/homebrew`、`/opt/local` | 路径数组直接补齐 | 只是多两个 `existsSync` 探测 |
| 4 | 书架去重 | `realpathSync.native` + NFC；POSIX 不替换反斜杠 | 按平台决定分隔符归一与小写；解析真实路径；NFC | Windows 仍做反斜杠归一 + 小写 |
| 5 | 安装门槛 | `engines.dsh` 降到 `>=0.2.1-rc.4` | 同 | 插件只用到 0.2.1 已存在的 API（核对过 `tools.register({when})`、`webServer`、`connection.requestRejection`、`agentPresets.presetForSession`、`agent/created`） |
| 6 | 预设挂载 | `tool-office` 缺包时 `disabled: !!js` | 同；缺包那行自动禁用，预设不再 `broken` | 有该包的版本上表达式返回 false，行照常启用 |
| 7 | 文案/提示词 | `pwsh` → 「终端」；插件卡片说明改写 | 同（宿主说明与中英文 locale） | 仅文字 |

## 3. 属于打包层的 3 项（无法靠写法消除，也不需要）

| 项 | 原因 | 主线当前处理 |
|---|---|---|
| 自带 `node_modules` | 插件以 `link:` 安装时 pnpm 不会为被链接包装依赖，缺依赖会在激活时 `ERR_MODULE_NOT_FOUND` | README 要求安装后在 `plugin/` 执行 `pnpm install --prod`；插件管理器安装时会处理 |
| 符号链接扁平化 | pnpm `.pnpm` 是符号链接，`ditto` 会把它改写成绝对路径 | 只有"带着 dependencies 直接复制"才遇到；按 README 安装不触发 |
| `.command` 一键安装器 | macOS 桌面双击安装 | 不放在通用包里，需要时单独提供 |

> 这三项不影响"同一份源码在 macOS 上运行"，只影响**不装依赖、直接拷贝**这种安装方式。

## 4. 平台事实 / 未解决

1. **系统通知**：DSH Host 以 `ELECTRON_RUN_AS_NODE` 运行，`require('electron')` 不可用。
   - macOS：已用 `osascript` 兜底，可用；
   - Windows / Linux：目前没有等价的系统级兜底（Windows 需 BurntToast 模块或 PowerShell toast 脚本，不保证可用）。
     表现为"插件内提醒正常，桌面通知不弹"。这属于平台能力问题，不是写法能完全解决的。
2. **PDF**：macOS 有 PDFKit；Windows/Linux 需要 `pdftotext`（poppler）。
   扫描件/图片型 PDF 两种引擎都抽不出（需 OCR，不在插件范围）。

## 5. 本次合并后的验证

- 宿主语法、客户端构建、两份冒烟全绿；
- 新增 `plugin/test/tools/runtime-probe.mjs`（来自 macOS 适配包）用于真实运行时探测：
  ```
  ELECTRON_RUN_AS_NODE=1 "<DSH 可执行文件>" plugin/test/tools/runtime-probe.mjs
  ```
  覆盖 `node:sqlite`、只读封印、`study_run_program`、目录扫描、PDF、原生通知；
- macOS 上的最终确认仍需在 Mac 上跑一次探针与页面检查（本工作区无 macOS 环境）。

## 6. 结论

除"打包时是否自带依赖"和"Windows/Linux 桌面通知"两点外，**0.9.35 起不再需要 macOS 专用构建**：
同一份发行包可直接在 macOS 上安装运行；`MacOS/` 里的适配包可以退役为参考资料。
